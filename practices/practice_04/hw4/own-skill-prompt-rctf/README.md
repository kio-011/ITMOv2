# prompt-rctf — самописный скилл

Собственная разработка, не установка готового скилла из чужого репозитория. Папка собрана для ревью: здесь сам скилл, его тесты и подтверждения запуска.

## Что делает

Превращает сырую просьбу в структурированный промпт по схеме **RCTF**: Role, Context, Task, Format. На выходе — текст промпта, который можно скопировать в любую LLM. Задачу из промпта скилл намеренно не выполняет.

Зачем: промпты по такой схеме пишутся постоянно и вручную, при этом стабильно теряются одни и те же вещи — конкретика в Format, факты в Context, одно действие в Task. Скилл задаёт правила, а скрипт детерминированно ловит типовые провалы формы.

## Состав

```

│   ├── SKILL.md                   # инструкция: контракт вывода, правила блоков, роутер материалов
│   ├── references/
│   │   ├── sources.md             # литература, разделённая по надёжности
│   │   ├── examples.md            # few-shot: пары «сырая просьба → промпт», слабый и исправленный
│   │   └── blocks.md              # заготовки формулировок для Role и Format
│   └── scripts/
│       ├── check_prompt.py        # валидатор структуры промпта (stdlib, без зависимостей)
│       └── test_check_prompt.py   # 30 тестов
└── evidence/

    ├── check_prompt_demo.txt      # работа валидатора на двух образцах
```

## Как устроен

**`SKILL.md`** содержит только то, что нужно всегда: контракт вывода, порядок работы, правила четырёх блоков и таблицу-роутер по материалам. Поле `description` во frontmatter — единственное, что постоянно висит в контексте модели, поэтому в нём перечислены формулировки-триггеры и явно сказано, когда скилл применять **не** нужно.

**`references/`** грузятся по требованию, а не при каждом вызове: `SKILL.md` указывает, какой файл читать в какой ситуации. Так подробные материалы не занимают контекст впустую.

**`scripts/check_prompt.py`** — автоматизация. Инструкцию модель может применить неточно, поэтому структура проверяется кодом. Что ловит:

| Проверка | Уровень |
|---|---|
| Отсутствует или пуст блок Context, Task, Format | ERROR |
| Format без конкретики (нет структуры и объёма) | ERROR |
| Осталась заглушка (`TODO`, `вставь сюда`, `<...>`) | ERROR |
| Нет блока Role | WARN (допустимо для фактических задач) |
| Украшения в роли: «гениальный», «мирового уровня», стаж в годах | WARN |
| Размытые слова: «качественно», «подробно», «максимально» | WARN |
| Context короче 40 символов или пересказывает Task | WARN |
| В Task несколько действий либо непрямое начало «мне нужно» | WARN |

Код возврата: 0 — ошибок нет, 1 — есть ошибки, 2 — файл не прочитан. Зависимостей нет, нужен только Python 3.

## На чём основаны правила

Разбор источников — в `prompt-rctf/references/sources.md`. Ключевое решение, отличающее скилл от пересказа популярных статей, касается блока Role.

Практические материалы советуют назначать модели развёрнутую экспертную персону. Эмпирика это не подтверждает: в работе [«When "A Helpful Assistant" Is Not Really Helpful»](https://arxiv.org/abs/2311.10054) проверили 162 персоны на четырёх семействах моделей и 2410 фактических вопросах — прироста относительно контроля без персоны не обнаружено. В [«Principled Personas»](https://arxiv.org/abs/2508.19764) показано, что экспертная роль даёт нулевой или небольшой плюс, но нерелевантные детали в её описании роняют качество почти на 30 процентных пунктов.

Поэтому в скилле Role — одно предложение без регалий, а для фактических задач её разрешено опускать. Валидатор помечает украшения и стаж.

Остальные правила опираются на систематический обзор [The Prompt Report](https://arxiv.org/abs/2406.06608) (более 1500 статей, таксономия 58 приёмов): отсюда few-shot из 2–5 разнородных пар «вход → выход» и требование конкретности. Отделение длинного материала тегами от инструкций — стандартная рекомендация документации вендоров.

Отдельно отмечено в `sources.md`: сам акроним RCTF в рецензируемой литературе не встречается, он из практических материалов и бытует в вариантах RCTF, RTCF, RTF. Это способ ничего не забыть, а не проверенный в экспериментах метод; доказательная база есть у отдельных приёмов внутри него.

## Как проверить самому

Сам валидатор работает на голом Python 3, ставить ничего не нужно. Для тестов требуется `pytest`: если его нет в системном интерпретаторе, подойдёт `uv run --with pytest pytest -q` или любой venv с pytest.

```bash
# тесты валидатора (нужен pytest)
cd prompt-rctf/scripts && python3 -m pytest -q

# валидатор на плохом промпте: 1 ошибка, 8 предупреждений, код 1
python3 prompt-rctf/scripts/check_prompt.py evidence/samples/weak_prompt.md

# на собранном по правилам: OK, код 0
python3 prompt-rctf/scripts/check_prompt.py evidence/samples/strong_prompt.md
```

## Как установить и вызвать

Скилл не установлен в этой папке намеренно: она собрана для чтения. Чтобы попробовать в работе, скопировать папку `prompt-rctf/` в `.claude/skills/` своего проекта и открыть новую сессию (скиллы читаются при старте):

```bash
mkdir -p <проект>/.claude/skills
cp -R prompt-rctf <проект>/.claude/skills/
```

Затем вызвать: `/prompt-rctf напиши тесты для эндпоинта статистики`.

## Результаты проверки

- `evidence/skill_tests.txt` — 30 тестов, все проходят.
- `evidence/check_prompt_demo.txt` — прогон валидатора на двух образцах: слабый промпт даёт 1 ошибку и 8 предупреждений с конкретными формулировками, собранный по правилам проходит чисто.

## Ограничения

- Валидатор проверяет **форму, а не смысл**: он не знает, верны ли факты в Context и уместна ли выбранная роль.
- Проверки на размытые слова и украшения — списки подстрок, русский и английский. Другой язык и неочевидные формулировки он пропустит.
- Разбор «несколько действий в Task» эвристический: редкие формулировки возможны мимо.
- Сам промпт составляет модель по инструкции; скилл повышает шанс хорошей формы, но не гарантирует качество содержания.
- Примеры в `references/examples.md` написаны автором скилла и покрывают четыре случая (разбор учебной темы, тесты к коду, разбор критериев задания, план занятия). Под другой набор задач их стоит заменить: для few-shot это важнее остального.
