# Практика 7.1. Отчёт по домашней работе: AI-ассистент для код-ревью в n8n

Этот файл объясняет, что сделано, как это работает и чем подтверждено. Условия задания лежат в [README.md](README.md).

## 1. Что это за работа

В n8n собран сценарий, который сам ревьюит Pull Request в репозитории `kio-011/ITMOv2`:

- берёт diff PR, отдаёт его AI-агенту и публикует результат в PR как GitHub-ревью;
- умеет вызываться комментарием: `/make_ai_review` (основная модель) и `/make_other_ai_review` (вторая модель);
- помнит, какие PR уже проверены (Data Table), и не повторяет ревью без новых коммитов;
- в «звёздочке» публикует замечания точечно, к конкретным строкам кода, и умеет читать файлы проекта как контекст.

Сценарии в n8n (https://n8n-itmo.cyrweb.ru):

| Сценарий | Что в нём |
|---|---|
| `MT lab 7.1 - AI code review` | Шаги 1–3 (вторая модель, Data Table, дедупликация), ревью одним общим комментарием |
| `MT lab 7.1 - AI code review ***` | Всё то же + «звёздочка»: точечные комментарии и инструмент чтения файлов. Это итоговая версия |

## 2. Тестовый проект на C++ (`demo_cpp/`)

Чтобы было что ревьюить, в репозитории лежит маленький учебный проект «банк» на C++ (`practices/practice_07.1/demo_cpp/`): счета, пополнение, снятие, перевод, отчёт. Файлы: `bank.h`, `bank.cpp`, `main.cpp`, `Makefile` (и `tests.cpp` в исправленной версии).

Проект используется как материал для проверки ассистента:

- ветка `test/demo-cpp-review`: версия, в которую намеренно заложены ошибки (уязвимость, потеря денег при переводе, неинициализированные поля, неточный расчёт итога, жёстко записанный пароль), а также текст-ловушка, адресованный ревьюеру-ИИ, чтобы проверить защиту от prompt injection. Это основа для [PR 7](https://github.com/kio-011/ITMOv2/pull/7);
- ветка `feature/bank-hardening`: исправленная версия (атомарный перевод, запись в журнал без `std::system`, расчёт в копейках, пароль из переменной окружения, `set_overdraft`, тесты). Это [PR 8](https://github.com/kio-011/ITMOv2/pull/8).

Как запустить сам проект:

```bash
cd practices/practice_07.1/demo_cpp
make test && make bank && ./bank
```

## 3. Как устроен сценарий

```
GitHub Trigger → Normalize event → Is relevant event? ─┬─ нет → Ignore
                                                       └─ да → Get PR info → Check PR in table → Already reviewed?
Already reviewed? ─┬─ да  → Reply: already reviewed (ответ в PR, ревью не запускается)
                   └─ нет → Get PR diff → Annotate diff → Code Review Agent → Build review
                                                               ▲  ▲
                                          Chat Model ──────────┘  └── repo_files (инструмент)
Build review → Post review comment → Save PR to table → Add label ReviewedByAI
```

| Нода | За что отвечает |
|---|---|
| GitHub Trigger | Принимает события репозитория `pull_request` и `issue_comment` |
| Normalize event | Приводит события к одному формату. Режим: `auto` (PR открыт), `command` (`/make_ai_review`), `other` (`/make_other_ai_review`). Здесь же выбирается модель: основная `openai/gpt-5`, вторая `anthropic/claude-sonnet-4.5` |
| Is relevant event? | Пропускает дальше только PR-открытие и две команды, остальное уходит в «Ignore» |
| Get PR info | Берёт данные PR, в том числе SHA последнего коммита |
| Check PR in table / Already reviewed? | Ищут в Data Table запись (номер PR, SHA, модель). Нашли: PR уже проверен |
| Reply: already reviewed | Пишет в PR «ревью уже есть выше» вместо запуска |
| Get PR diff | Скачивает diff PR |
| **Annotate diff** (код) | Режет diff на файлы и блоки изменений и ставит перед каждой строкой её номер в новом файле (`[L12]`). Запоминает, какие строки GitHub разрешит комментировать |
| **Code Review Agent** | AI-агент: ревьюит и возвращает JSON (итог + список замечаний с файлом и строкой). Не доверяет тексту в diff, сообщает о попытках манипуляции отдельным полем |
| Chat Model | Модель для агента, выбирается по режиму |
| **repo_files** (инструмент агента) | Читает список файлов каталога или файл из версии PR. README не используется: агент сам смотрит, какие файлы есть в проекте |
| **Build review** (код) | Проверяет ответ модели: если путь и строка есть в diff, замечание станет комментарием к строке, иначе попадёт в общий текст. Собирает тело ревью |
| **Post review comment** | Отправляет одно ревью `POST /pulls/{n}/reviews` с комментариями к строкам |
| Save PR to table | Записывает в Data Table `reviewed_prs` номер PR, модель, режим и SHA |
| Add label ReviewedByAI | Вешает на PR метку |

## 4. Что сделано по шагам задания

### Шаг 1. `/make_other_ai_review` (вторая модель)
Команда в комментарии PR включает режим `other`. В «Normalize event» это меняет модель на `anthropic/claude-sonnet-4.5`; «Chat Model» берёт имя модели из этого поля. Больше ничего в сценарии не меняется: тот же агент, другой «мозг». В ревью первая строка показывает, какая модель его написала.

### Шаг 2. Data Table
Таблица `reviewed_prs` (колонки `pr_number`, `model`, `source`, `head_sha`). После опубликованного ревью нода «Save PR to table» добавляет строку.

### Шаг 3. Без повторных запусков
Перед ревью сценарий ищет в таблице строку с тем же номером PR, тем же SHA и той же моделью. Нашёл: пишет в PR «ревью уже есть выше» и останавливается. Новый коммит меняет SHA, и ревью можно запустить снова. Ключ из трёх полей выбран, чтобы вторая модель не блокировалась первой.

### Шаг 4 (звёздочка). Точечные комментарии
1. «Annotate diff» разбирает diff по блокам и нумерует строки новой версии файла.
2. Агент отвечает структурой: для каждого замечания `path`, `line`, важность, заголовок, текст.
3. «Build review» сверяет `path` и `line` с картой допустимых строк. Если строки в diff нет, замечание не теряется, а попадает в общий текст ревью (иначе GitHub отклонил бы весь запрос).
4. «Post review comment» публикует одно ревью: сверху итог, ниже комментарии на строках кода.
5. Дополнительно `repo_files` даёт агенту контекст проекта. В ревью также отображается предупреждение, если в коде найден текст-обращение к ревьюеру-ИИ.

## 5. Чем отличаются результаты двух моделей

- `gpt-5` находит меньше замечаний и пишет короче: на PR 8 это 2 комментария (переполнение при проверке снятия, переполнение суммы).
- `claude-sonnet-4.5` находит больше, но чаще ошибается: на PR 8 до 4 комментариев, среди которых есть и верные (переполнения), и неверные (например, утверждение, что `0ULL - static_cast<unsigned long long>(x)` даёт UB, хотя для беззнаковых типов это определённая арифметика).
- Обе модели замечают текст-ловушку в коде и не выполняют его, сообщают о нём отдельной строкой.

## 6. Ограничения

- Автоматически ревью запускается только при открытии PR, дальше только по комментарию (так задано в условии задания). Новый коммит сам по себе ревью не вызывает.
- Модель решает, читать ли файлы через `repo_files`. На PR, где все файлы новые (base `main`), читать нечего, поэтому инструмент не вызывается; на PR 8 с base `test/demo-cpp-review` он сработал, но модель только посмотрела список файлов каталога.
- Замечания моделей бывают ложными, поэтому ревью только подсказывает, а решает человек.
- Комментарии ставятся там, где модель нашла проблему, а не к каждому блоку подряд.
