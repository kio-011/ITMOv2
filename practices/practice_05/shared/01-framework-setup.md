# Spec Kit: что установлено и чем он отличается от OpenSpec

**Установка уже выполнена** — в `team-ui/` и `team-logic/` отдельно. Этот файл описывает
получившуюся конфигурацию и служит черновиком для `06-framework-comparison.md`.

## Что именно стоит

```bash
uvx --from git+https://github.com/github/spec-kit.git \
  specify init --here --force --non-interactive --integration claude --script sh
```

Версия, установленная 2026-10-29: коммит `99e047e`.

Важно: интерфейс CLI поменялся по сравнению с большинством гайдов в сети.
Флага `--ai` больше нет — теперь `--integration`. Команды называются через **дефис**,
а не через точку: `/speckit-specify`, не `/speckit.specify`. Все промпты в этой папке
уже исправлены.

## Что появилось в каждой папке команды

```
team-ui/
├── .claude/skills/        10 навыков speckit-*
└── .specify/
    ├── memory/constitution.md    правила проекта
    ├── templates/                spec, plan, tasks, checklist, constitution
    ├── scripts/bash/             создание фичи, подготовка плана и задач
    └── workflows/                реестр workflow
```

Спецификация появится в `team-ui/specs/001-<имя>/spec.md` — **внутри папки команды**,
не в корне репозитория. Проверено прогоном `create-new-feature.sh --dry-run`:
корнем считается ближайшая папка с маркером `.specify/`, а не корень git.

## Команды

Основной путь:

| Команда | Что делает |
|---|---|
| `/speckit-constitution` | фиксирует принципы проекта |
| `/speckit-specify` | создаёт спецификацию из описания на человеческом языке |
| `/speckit-plan` | план реализации: стек, архитектура, решения |
| `/speckit-tasks` | разбивает план на задачи |
| `/speckit-implement` | выполняет задачи |
| `/speckit-converge` | сверяет код с задачами и дописывает оставшуюся работу |

Дополнительные:

| Команда | Что делает |
|---|---|
| `/speckit-clarify` | задаёт структурированные вопросы по неоднозначным местам, до плана |
| `/speckit-analyze` | отчёт о согласованности спеки, плана и задач |
| `/speckit-checklist` | генерирует чек-лист качества требований |
| `/speckit-taskstoissues` | выгружает задачи в issues |

## Принципиальные отличия от OpenSpec

### 1. Единица работы: фича против изменения

OpenSpec мыслит **изменениями системы**: `openspec/changes/<change>/` с proposal, design,
tasks и дельтами спек. Spec Kit мыслит **фичами**: `specs/001-<имя>/` со spec, plan,
tasks. Отсюда разница в вопросе: OpenSpec спрашивает «что меняется в системе», Spec Kit —
«что мы строим».

### 2. Накопительная база требований против истории решений

Главное отличие. В OpenSpec `/opsx:archive` переносит change в архив и **сливает дельты
в `openspec/specs/`** — постоянные capability-спеки, которые всегда отвечают «как система
работает сейчас». В subtracker их шесть, они пережили три изменения.

В Spec Kit такого слоя нет вообще. `specs/001-…`, `specs/002-…` — это история
принятых решений. На вопрос «как сейчас работает авторизация» Spec Kit не отвечает:
надо читать все фичи, которые её касались, и держать в голове порядок.
Ответ на этот вопрос в Spec Kit — сам код.

### 3. Уточнение вынесено в отдельную фазу

В OpenSpec уточнение требований растворено внутри `/opsx:propose`. В Spec Kit это
отдельная команда `/speckit-clarify`, которую запускают осознанно и до плана.
Для ДЗ 5 это удачно: фаза, на которой вопросы задаются явно, — ровно то место, где
видно, какие вопросы каждая команда решила за другую.

### 4. Есть проверка согласованности артефактов

`/speckit-analyze` сверяет спеку, план и задачи между собой и выдаёт отчёт о
расхождениях. В OpenSpec такой команды нет — согласованность держится на ревью
человеком. Плюс `/speckit-checklist`, который генерирует чек-лист полноты требований.

### 5. Нет шага архивации

В OpenSpec завершение — явный ритуал: `/opsx:archive`, change уезжает в
`changes/archive/<дата>-<имя>/`, спеки обновляются. В Spec Kit фича просто остаётся
в `specs/` навсегда. Мусор никто не убирает, «готово» и «в работе» внешне неразличимы.
Зато есть `/speckit-converge` — сверка кода с задачами, чтобы понять, что ещё не сделано.

### 6. Правила проекта: конституция против AGENTS.md

OpenSpec опирается на `AGENTS.md` — обычный markdown, читается всеми агентами.
Spec Kit держит `.specify/memory/constitution.md` по своему шаблону, с версионированием
принципов. Формальнее, но живёт отдельно от `AGENTS.md`, и их легко рассинхронить.

### 7. Привязка к ветке и к состоянию

Старые версии Spec Kit переключали git-ветку на каждую фичу. Установленная версия
этого **не делает** — состояние хранится в `.specify/feature.json` и переменных
`SPECIFY_FEATURE` / `SPECIFY_FEATURE_DIRECTORY`. Для нашей схемы это критично: две
команды работают в одном репозитории и не дерутся за ветку.

## Изоляция команд

Изоляция сделана не worktree, а **папками с собственным корнем Spec Kit**:

- `team-ui/` и `team-logic/` — каждая со своим `.specify/` и `.claude/skills/`;
- внутри каждой лежат своя копия `00-shared-context.md`, `02-constitution.md`
  и `fixtures/statement-sample.csv`, чтобы агенту вообще не требовалось выходить наружу;
- в пре-промпты и в промпты генерации и ревью вписан явный запрет читать что-либо
  за пределами своей папки.

Запрет — это инструкция, а не песочница: агент технически может выйти. Поэтому
стоит запускать чаты с рабочей директорией, установленной в папку команды, и
проверять по логу инструментов, что чтений наружу не было.
