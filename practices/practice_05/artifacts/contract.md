# Общий контракт — импорт банковской выписки

Принят 2026-10-29 по итогам сведения двух независимых спецификаций
(`artifacts/before/ui-spec.md`, `artifacts/before/logic-spec.md`).

**Статус документа.** Контракт главнее обеих спек. Там, где спека расходится с
контрактом, меняется спека. Решения приняты человеком; обоснование и отклонённые
варианты сохранены, чтобы к ним можно было вернуться.

---

## 1. Глоссарий

Один термин — одно определение. Обе команды используют только эти слова.

| Термин | Определение |
|---|---|
| **Импорт** | один факт загрузки одного файла одним владельцем. Имеет идентификатор, статус и срок жизни. |
| **Кандидат** | группа операций выписки, признанная похожей на подписку. Существует на сервере, принадлежит импорту, имеет идентификатор. |
| **Операция кандидата** | одна строка выписки, отнесённая к кандидату: дата, сумма, исходное описание, номер строки. |
| **Совпадение** | связь кандидата с уже существующей подпиской владельца: `none`, `exact`, `amount_differs`, `cycle_differs`. |
| **Подтверждение** | одно неделимое действие, превращающее выбранных кандидатов в подписки. |
| **Основной список** | кандидаты, которые сервер считает надёжными. |
| **Список «требует проверки»** | кандидаты, собранные из 1–2 операций или со слабыми основаниями. |
| **Метка уровня** | `high` / `medium` / `low` — единственная характеристика надёжности, доступная клиенту. |
| **Пропущенная строка** | строка файла, которую не удалось разобрать. Не ошибка импорта. |
| **Отсеянная группа** | разобранные операции, не ставшие кандидатом (разовая покупка, приход, перевод). |

Слова **«черновик»**, **«задача разбора»**, **«рекомендуемый порог»** из контракта
исключены: они обозначали сущности, которых в итоге нет.

## 2. Карта расхождений

### Данные

| Что | UI | Логика | Тип |
|---|---|---|---|
| кандидат как сущность | только в ответе, идентификатора нет | запись на сервере с идентификатором | противоречие |
| надёжность | «ровно три уровня, без чисел» | метка из трёх + признак отметки + два списка | **совпало** |
| правка перед сохранением | + активность, − дата начала, − заметка | 7 полей, лишнее → `422` | расхождение в одном поле |
| сумма | строка, 2 знака | строка, 2 знака | **совпало** |
| валюта | одна на профиль | одна на профиль | **совпало** |

### Вызовы

| Что | UI | Логика | Тип |
|---|---|---|---|
| число запросов | один (загрузка) | четыре (загрузка, чтение, подтверждение, отказ) | пробел у UI |
| ключ идемпотентности | не упомянут | обязателен, генерирует клиент | **молчаливое допущение с обеих сторон** |
| отказ от импорта | не вызывается | `DELETE`, иначе копятся | пробел у UI |
| действие на элементе | не отправляется | обязательно, иначе `422` | **блокирующее противоречие** |

### Ошибки

| Что | UI | Логика | Тип |
|---|---|---|---|
| размер файла | 5 МБ | 2 МиБ | разные числа, обе обоснованы |
| обрыв разбора | ждёт 30 с | рвёт на 10 с | разные числа |
| частота загрузок | состояния нет | 10/час, `429` | пробел у UI |
| полностью битый файл | состояния нет | правило удалено | **совпало после ревизии** |
| формат ошибки | код + параметры, словарь на клиенте | то же | **совпало** |

### Состояния

| Что | UI | Логика | Тип |
|---|---|---|---|
| где живёт разбор между шагами | нигде, после перезагрузки заново | на сервере, TTL, `GET` | противоречие |
| повторное подтверждение | блокировка кнопки | идемпотентность по ключу | пробел у UI |
| откат | кнопка на экране итога | «отката нет» | противоречие |
| предел активных импортов | не знает | 3, отказ на четвёртом | пробел у UI |

## 3. Принятые решения

### Р1. Обновление существующей подписки — включаем, но узко

**Варианты.** (а) убрать обновление, как хотел UI: дубликат можно только пропустить или
завести второй; (б) оставить как у логики: любое поле, любая цель, обязательный `action`
на каждом элементе.

**Решение.** Обновление остаётся, но сужено до одного случая:

- доступно **только** при `duplicate_match = "amount_differs"`;
- меняется **только** `amount`;
- цель — подписка, которую нашёл сервер; выбрать другую нельзя;
- `expected_amount` обязателен: если текущая сумма целевой подписки не равна ему,
  элемент отклоняется с `confirm.amount_conflict` (владелец правил подписку в другой
  вкладке);
- ответ возвращает `previous.amount` и `current.amount`.

**Почему.** Полный отказ от обновления делает самый интересный случай фикстуры (Netflix
`15.49` → `17.99`) вечным дубликатом — ради этого фича и затевалась. Полная версия
логики тянет выбор произвольной цели, произвольные поля и невозможность отката: это
недели работы и необратимое изменение чужих данных. Узкий вариант закрывает реальную
боль и оставляет изменение обратимым (прежняя сумма известна).

### Р2. `action` обязателен только там, где есть выбор

Поле `action` обязательно для элемента с `duplicate_match ≠ "none"`. Для кандидата без
совпадений оно необязательно; его отсутствие означает `create`.

**Почему.** Логика требовала `action` на каждом элементе, защищая принцип «не менять
данные владельца молча». Но у кандидата без совпадений менять нечего — единственное
допустимое значение одно. Обязательное поле с одним легальным значением не защищает ни
от чего и гарантирует `422` любому клиенту, который о нём не знал. Защита остаётся ровно
там, где есть риск.

*Возражение логики сохранено: единообразие контракта. Отклонено — цена единообразия
здесь выше его пользы.*

### Р3. Импорт хранится на сервере; клиент работает по идентификатору

Принимается модель логики целиком: импорт и кандидаты — записи на сервере.

- **TTL импорта в статусе `analyzed` — 2 часа** (не 24: разбор не возобновляют через сутки,
  а длинный TTL упирается в предел активных импортов).
- Клиент **обязан** вызывать `DELETE`, когда владелец закрывает процесс.
- Предел — 3 активных импорта. При попытке создать четвёртый сервер отвечает
  `409 import.too_many_active` **и возвращает список активных импортов** (идентификатор,
  имя файла, время загрузки), чтобы клиент предложил отказаться от старого и повторить.
  Молчаливого вытеснения нет.

**Следствие для UI:** текст `import.draft.lost` удаляется. После перезагрузки страницы
список кандидатов восстанавливается по `import_id` — возможность, от которой UI отказался,
не зная, что она есть.

### Р4. Ключ идемпотентности генерирует клиент

- Клиент создаёт `idempotency_key` при открытии экрана подтверждения.
- **Клиент создаёт новый ключ при любом изменении состава**: выбор кандидата, снятие
  выбора, правка поля, смена действия.
- Повтор после сетевой ошибки отправляется **с тем же ключом**.
- `409 confirm.idempotency_key_reused` — признак дефекта клиента, а не рабочий путь.

**Почему.** Формальное определение равенства состава (канонизация, сортировка, сравнение
кортежей) остаётся на сервере как проверка. Клиенту навязывать его вычисление не нужно:
правило «состав изменился → новый ключ» проще и даёт тот же результат.

### Р5. Размер файла — 2 МиБ

Выигрывает число сервера: он единственный, кто его обеспечивает. 5 МБ у клиента
означали бы `413` после ожидания загрузки. Клиент показывает «до 2 МиБ» в подсказке и
проверяет размер до отправки.

### Р6. Ожидание — 15 секунд у клиента, обрыв — 10 у сервера

Клиент обязан ждать дольше, чем сервер готов работать, иначе он покажет свой таймаут
поверх уже идущего ответа. 10 с (обрыв) + запас на сеть = 15 с. Текст «это может занять
до 30 секунд» заменяется на «до 15 секунд».

### Р7. Предел частоты остаётся, у клиента появляется состояние

10 загрузок в час. Неудачные загрузки (нечитаемый файл, превышение размера) **не
считаются**. В ответе `429` — время следующей возможной попытки; клиент показывает его
текстом, а не общей ошибкой сервера.

### Р8. Надёжность: контракт сервера принимается целиком

Клиент получает: два списка, `preselect_recommended`, метку уровня из трёх значений,
структурные основания. Клиент **не читает** числовую `confidence` и не сравнивает ничего
с порогами.

**Маппинг трёх групп интерфейса на контракт:**

| Группа UI | Правило |
|---|---|
| «Уже есть у вас» | `duplicate_match ≠ "none"`, независимо от списка |
| «Нашли подписки» | основной список, `duplicate_match = "none"` |
| «Возможно, подписки» | список «требует проверки», `duplicate_match = "none"` |

Отмечены по умолчанию — ровно те, у кого `preselect_recommended = true` **и**
`duplicate_match = "none"`.

### Р9. Откат — ограниченный, без серверной операции

- Созданные подписки удаляются существующим `DELETE /api/subscriptions/{id}`.
- Обновлённая сумма возвращается существующим `PATCH` на значение `previous.amount`
  из ответа подтверждения.
- Доступно, пока открыт экран итога. Состояние прерванной отмены описывает UI.
- Отдельной серверной операции отката нет.

Это работает только потому, что Р1 сузил обновление до одного поля и вернул прежнее
значение в ответе.

### Р10. Частичный разбор — всегда успех с предупреждением

Порога «доля брака, при которой файл отклоняется», нет (обе стороны пришли к этому сами).
Сервер отдаёт `incomplete_data: true`; клиент **обязан** показать предупреждение, когда
он выставлен, и не блокирует подтверждение.

### Р11. Набор правок при создании

`name`, `amount`, `billing_cycle`, `custom_interval_days`, `next_billing_date`.

- `start_date` и `note` сервер принимает, клиент не отправляет (дата начала показывается
  только для чтения как факт из файла).
- Поля «активна / приостановлена» не существует: все созданные импортом подписки активны.

### Р13. Частичный результат подтверждения — нормальный путь (правка от 2026-10-29)

**Исправление дефекта контракта.** Раздел 5 первой редакции называл подтверждение
«атомарным: либо выполнены все элементы, либо ни один». Это неверно прочитало правило
сервера: неделима только группа успешных элементов (`created` + `updated`), а элемент,
не прошедший проверку, исключается из неё и попадает в `skipped`, не отменяя остальных.
UI добросовестно выполнил контракт и удалил состояние «сохранено частично» — в
результате самый вероятный исход новой фичи остался непокрытым.

**Решение.**

- Подтверждение возвращает `201` даже когда часть элементов не выполнена. Ответ содержит
  `created`, `updated` и **непустой** `skipped` с кодом причины по каждому элементу.
- `confirm.amount_conflict` — **не ошибка запроса, а причина пропуска элемента**:
  сумма целевой подписки изменилась между разбором и подтверждением. Остальные
  подписки при этом создаются.
- `422 confirm.all_items_failed` возвращается только если не выполнен **ни один**
  элемент; импорт остаётся `analyzed`.
- **Уточнение по предложению серверной команды (принято).** Если не выполнен ни один
  элемент и причина у всех одна, возвращается **эта причина**, а не общий
  `confirm.all_items_failed`. В частности, единственный элемент с конфликтом суммы даёт
  `422 confirm.amount_conflict`. Так клиент получает одинаковую причину независимо от
  того, был элемент один или в наборе. Серверная команда отметила расхождение прочтений
  в своей спеке — вопрос закрыт в пользу её варианта, он информативнее.
- Если выполнен хотя бы один элемент, импорт переходит в `confirmed`; повторное
  подтверждение пропущенных элементов в этой итерации **невозможно** (статус
  терминальный) — владелец заводит их обычным добавлением подписки.
- Коды пропуска элемента отделены от кодов ответа: `item.invalid_value`,
  `confirm.amount_conflict`. Клиент обязан иметь текст для каждого.

**Почему так, а не «делать подтверждение по-настоящему атомарным».** Атомарность по
всему набору означала бы, что одна подписка, изменённая владельцем в другой вкладке,
отменяет импорт девяти других. Это хуже для владельца и провоцирует повторные попытки.

### Р12. Тексты

Сервер отдаёт `code` + `params`, прозы не присылает. Клиент собирает текст по словарю
ru/en. Обязательство с обеих сторон: **каждый код из таблицы раздела 6 имеет ключ в
словаре на обоих языках**, и это проверяется тестом.

## 4. Модель данных на границе

Поля в `snake_case`. Суммы и длительности — строки. Даты — `YYYY-MM-DD`.

**Кандидат:**

| Поле | Тип | Обяз. | Примечание |
|---|---|---|---|
| `candidate_id` | строка | да | |
| `name` | строка | да | |
| `amount` | строка, 2 знака | да | последняя сумма из выписки |
| `previous_amount` | строка, 2 знака | нет | только при шаге цены |
| `billing_cycle` | `monthly`/`yearly`/`weekly`/`custom_days` | да | |
| `custom_interval_days` | целое | только при `custom_days` | |
| `start_date` | дата | да | первая дата в выписке, только для чтения |
| `suggested_next_billing_date` | дата | да | |
| `occurrence_count` | целое | да | |
| `first_seen`, `last_seen` | дата | да | |
| `cycle_basis` | `intervals`/`single_interval`/`text` | да | основание вывода цикла |
| `amount_stability` | `stable`/`price_step`/`single`/`unstable` | да | |
| `confidence_label` | `high`/`medium`/`low` | да | |
| `preselect_recommended` | логическое | да | |
| `duplicate_match` | `none`/`exact`/`amount_differs`/`cycle_differs` | да | |
| `matched_subscription` | объект `{id, name, amount, billing_cycle}` | при `≠ none` | |
| `occurrences` | массив `{line, date, amount, raw_description}` | да | обоснование на экране |

`confidence` и `confidence_parts` — диагностика, клиент их не использует.

**Импорт:** `import_id`, `status` (`analyzed`/`confirmed`/`discarded`/`expired`),
`expires_at`, `ruleset_version`, `statement` (имя файла, кодировка, разделитель, валюта,
период, `rows_total`, `rows_parsed`, `rows_skipped`, `incomplete_data`, `skipped_rows`
до 100, `skipped_by_code`, `rejected_groups`), `candidates`, `candidates_review`.

**Существующая модель подписки не меняется.** Связь «создана импортом» хранится на
стороне кандидата.

## 5. Последовательность вызовов

```
1. POST   /api/imports/statement              multipart, поле file          → 201 импорт + кандидаты
2. GET    /api/imports/statement/{id}         после перезагрузки страницы   → 200 тот же импорт
3. POST   /api/imports/statement/{id}/confirm idempotency_key + items       → 201 created/updated/skipped
4. DELETE /api/imports/statement/{id}         владелец закрыл процесс       → 204
```

- Шаг 2 не обязателен в счастливом пути; обязателен после перезагрузки.
- Шаг 4 обязателен при отказе — иначе импорт займёт один из трёх слотов до истечения TTL.
- Шаг 3 синхронный, до 200 элементов. Атомарность — **частичная**, см. Р13: элемент,
  отклонённый проверкой, попадает в `skipped`, остальные выполняются.
- Все операции требуют того же `Bearer`-токена, что существующие ресурсы, и работают
  только с данными владельца.

## 6. Ошибки

| Код | Код ошибки | Что делает клиент |
|---|---|---|
| `400` | `statement.empty`, `statement.undecodable`, `statement.delimiter_unknown`, `statement.missing_columns`, `statement.unparsable`, `statement.no_outflows_detected` | текст по коду, действия «выбрать другой файл» |
| `401` | `auth.required` | возврат в поток после входа, выбранный файл сохраняется |
| `404` | `import.not_found`, `candidate.not_found` | импорт устарел — «начать заново» |
| `409` | `import.already_confirmed` | экран итога по ранее созданным подпискам |
| `409` | `confirm.idempotency_key_reused` | дефект клиента; общий отказ + отчёт |
| `409` | `import.too_many_active` | список активных импортов, предложение отказаться от старого |
| `410` | `import.expired` | «срок истёк, загрузите файл заново» |
| `413` | `statement.too_large` | предел и фактический размер |
| `415` | `statement.unsupported_media_type` | перечень допустимых форматов |
| `422` | `statement.too_many_rows` | предел и фактическое число |
| `422` | `confirm.nothing_selected`, `confirm.duplicate_candidate`, `confirm.unknown_field`, `confirm.action_required`, `confirm.target_required`, `confirm.malformed_value` | ошибка у конкретного поля или кандидата |
| `422` | `confirm.update_not_allowed` | обновление запрошено для кандидата, у которого совпадение не `amount_differs` — дефект клиента (добавлено при реализации, Р1) |
| `422` | `confirm.all_items_failed` | ничего не создано, список причин |
| `429` | `import.rate_limited` | время следующей попытки |

**Коды пропуска элемента** (не коды ответа, приходят в `skipped` при `201`):

| Код | Что означает | Что делает клиент |
|---|---|---|
| `confirm.amount_conflict` | сумма целевой подписки изменилась между разбором и подтверждением | экран итога показывает элемент как непринятый с причиной |
| `item.invalid_value` | значение поля не прошло проверку | то же, с указанием поля |
| `503` | `statement.analysis_timeout` | «повторить» доступно |

**Неизвестный код.** Клиент обязан иметь общий путь: нейтральный текст, действия
«повторить» и «начать заново», состав экрана не ломается.

## 9. Открытые вопросы — сознательно отложены

| Вопрос | Почему отложен |
|---|---|
| Мультивалютный импорт | требует изменения модели (одна валюта на владельца) — выход за принцип «модель не меняем» |
| Постоянная пометка «создана импортом» | требует поля в модели подписки; пока живёт на сессию |
| Возврат к тому же импорту после подтверждения | статус `confirmed` терминальный; добавить второй заход можно позже, ведя «использованность» на кандидате |
| Список «что мы не взяли и почему» | сервер отдаёт только счётчики по причинам; полный список — следующая итерация |
| Обновление цикла и других полей существующей подписки | Р1 сузил обновление до суммы |
