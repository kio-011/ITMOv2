# Проблема и метрики

Summary: добавленный API и сервис не соблюдают обязательные правила (SEC-1, API-1, REL-1, OUT-1, OBS-1), что ведёт к некорректному контракту ответа, отсутствию ограничений и необработанным сбоям при вызове LLM.

## Проблема

- Пользователь: разработчик или CI, отправляющий PR diff на ревью.
- Ситуация: вызывает POST `/api/reviews` с `diff`.
- Что происходит сейчас: сервис передаёт сырой `diff` во внешний LLM без фильтрации/лимитов, не задаёт таймаут, возвращает `{"comment": "..."}` вместо требуемой структуры; отсутствует контролируемая обработка ошибок и минимальное логирование.
- Почему это мешает пользователю или бизнесу: несоблюдение контракта и правил повышает риск утечек секретов, падений с 5xx, неустойчивой работы и невозможности автоматической обработки результата.
- Что не входит в задачу: реализация GitHub-операций, автопринятие/merge, генерация кода (SCOPE-1).

## Метрики

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля ответов в требуемом формате (OUT-1) | < 10% (по логике кода — ответ неструктурирован) | ≥ 99% | После деплоя | Интеграционные тесты API |
| Ошибки 5xx при таймауте LLM (REL-1) | > 0% (нет обработки) | 0% | При симулированном таймауте | Тесты/обсервабилити |
| Отклонения длинных диффов > 20000 симв. (API-1) | 0% | 100% с HTTP 413 | На нагрузочных тестах | Тесты API |

## Почему изменение метрики подтвердит решение проблемы

- Формат и контролируемые ошибки обеспечивают соответствие контракту и предсказуемость интеграций; лимит длины исключает перегрузку/злоупотребления.

## Как использовали AI

- Для чего: формализация проблемы и метрик на основе TRAINING_PR.diff и правил.
- Тип промпта: zero-shot и master prompt.
- Строка в [`prompts.md`](prompts.md): P1-01, Master Prompt v1.
- Что проверили и исправили сами: соответствие выводов строкам diff (evidence) и правилам; отсутствие неподтверждённых гипотез.
