# R.C.T.F.

Файл ведёт OpenCode по вашим запросам. Агент записывает фактические результаты экспериментов и вносит изменения в связанные файлы. Свою оценку сообщайте ему в чате; вручную заполнять шаблон не нужно.

- **Role:**
  Ты выступаешь в роли Performance/SRE-инженера, отвечающего за проектирование, проверяемость и воспроизводимость плана нагрузочного тестирования сервиса «ревью PR по diff». Твоя зона ответственности:
  - Спроектировать профиль трафика и набор сценариев так, чтобы решения по каждому сценарию были бинарными (PASS/FAIL), а допущения — явно отмечены.
  - Однозначно зафиксировать режим генерации нагрузки (VUs или constant-arrival-rate), окна прогрева/измерений, think time, SEED для повторяемости результатов.
  - Определить пороги p50/p95/p99, 4xx/5xx, долю 413 для больших diff и влияние «больших» на «обычные» запросы; для каждого численного параметра указать источник (подтверждено) или пометку «допущение» с TODO по валидации.
  - Описать метод инъекций деградаций LLM (мок/прокси/фича‑флаг), диапазоны задержек и доли инъекций, таймауты клиента/сервера (со ссылкой на конфиг/ADR или как допущение).
  - Задать конкретные метрики/лейблы/дашборды и перечень evidence (summary JSON, скриншоты/ссылки на дашборды, 3 трассы на p95) для каждого прогона.
  - Исключить домыслы: если нет источника — явно отмечай допущение и указывай, как его подтвердить.
  - Сохранить итоговый переработанный текст в файл артефакта: practices/practice_02/artifacts/load/test_load_rctf.md (артефакты/лоад/тестлоад_rtcf).

- **Context:**
  - Исходный артефакт practices/practice_01/tests_load.md описывает 5 сценариев: база (POST /api/reviews, малые diff), большие diff (ожидание 413), деградация внешнего LLM, soak (устойчивость), stress ramp (точка насыщения). Пороги p95/p99/4xx/5xx заданы, evidence описаны общо.
  - TRAINING_PR.diff: FastAPI POST /api/reviews → ReviewService.review(diff) → LLM.generate → JSON {"comment": ...}. Поведение 413 для слишком больших diff — ожидаемое требование из tests_load.md, требующее подтверждения ссылкой (спека/ADR) или пометки как допущение до подтверждения.
  - Пробелы текущего плана: нет чёткой модели генерации нагрузки (VUs vs arrival‑rate), SEED и окон измерений, конкретного механизма инъекций LLM‑задержек, точных имён метрик/дашбордов, формальной модели распределений размеров diff и явных источников SLO/порогов.

- **Task:**
  - Переработать раздел «Нагрузочные проверки» в воспроизводимый тест‑план с измеримыми критериями по каждому из 5 сценариев.
  - Добавить разделы: «Профиль трафика и данные», «Инструменты и запуск», «Pass/Fail Gate», «Наблюдаемость и evidence», «Инъекции и ограничения», «Реплицируемость и допущения».
  - Для каждого численного параметра указать статус: подтверждено (со ссылкой на файл/раздел) или допущение (с TODO по валидации).
  - Выбрать и зафиксировать единый способ генерации нагрузки (например, k6 + constant‑arrival‑rate), параметры запуска (прогрев, окно измерений, think time, SEED).
  - Прописать Pass/Fail для 5 сценариев, включая влияние «больших diff» на «обычные» запросы и правила фиксации точки насыщения.
  - Уточнить метод инъекций LLM‑деградаций (мок/прокси/фича‑флаг), таймауты клиента/сервера, доли/задержки инъекций (со ссылкой или как допущение).
  - Задать конкретные имена метрик/лейблов/дашбордов и перечень evidence для каждого прогона.
  - Сформировать список минимальных точечных правок к текущему tests_load.md и подготовить «Новый текст для вставки в tests_load.md».
  - Явно указать: «Сохранить переработанный текст в practices/practice_02/artifacts/load/test_load_rctf.md (артефакты/лоад/тестлоад_rtcf)».

- **Format:**
  Верни результат строго в следующей структуре и порядке (ровно 12 разделов):
  1. Переработанный план нагрузочного тестирования (R.C.T.F.)

  11. Инструкция по артефакту: «Сохранить в practices/practice_02/artifacts/load/test_load_rctf.md (артефакты/лоад/тестлоад_rtcf)»
  12. После выполнения заполни в этом файле (rctf/experiment.md) разделы «Что получили» и «Что изменили в исходном артефакте».
  Требования к содержанию:

  - Любая цифра помечается как [подтверждено] или [допущение] с ссылкой/TODO.
  - В «Pass/Fail Gate» оформи по каждому сценарию мини‑таблицу: Параметр | Значение | Статус | Источник/TODO.
  - В «Наблюдаемость и evidence» перечисли 3–5 конкретных метрик (точные имена/лейблы) и 2–3 дашборда.
  - Раздел «Новый текст…» помести в один fenced code block ```md ... ```; текст — самодостаточный (без ссылок на этот промпт) и готов к замене в файле.
  - Не включай скрытые рассуждения; не добавляй разделов вне списка.

## Полный запрос

Role:
Ты — Performance/SRE-инженер. Твоя задача — минимальными, но достаточными правками превратить существующий practices/practice_01/tests_load.md в инженерно строгий, воспроизводимый план нагрузочного тестирования с бинарными Pass/Fail критериями, конкретной наблюдаемостью и требуемым набором evidence. 2) Для каждого численного параметра укажи статус: подтверждено (со ссылкой) / допущение (с TODO по валидации).
3) Определи режим генерации нагрузки и параметры запуска (например, k6 + constant‑arrival‑rate; прогрев N минут; окно измерений M минут; think time; SEED).
4) Сформулируй Pass/Fail для 5 сценариев, включая влияние «больших diff» на «обычные» запросы и критерии фиксации точки насыщения.
