# Практика 7.2. Отчёт: классификация GitHub Issues в n8n

Условия задания лежат в [README.md](README.md). Этот файл описывает, что сделано. Сейчас готова **часть 1** (классификация Issues, эскалация, sub-workflow). Часть 2 (еженедельная статистика в Gmail) и задание со звёздочкой пока не сделаны.

## 1. Что это за работа

Автоматизация обращений в репозитории. Когда кто-то открывает новый Issue, n8n сам определяет его тип нейросетью, ставит нужный лейбл и, если уверен, оставляет комментарий-шаблон. Если не уверен, Issue получает лейбл `needs-triage` и комментария нет: пусть разберётся человек.

Тестовый репозиторий: https://github.com/kio-011/subtracker (проект «трекер подписок», Issues включены). В нём заведены лейблы `bug`, `task`, `feature-request`, `needs-triage`.

## 2. Два сценария и как они связаны

| Сценарий в n8n | Роль |
|---|---|
| `MT 7.2 base` | **Основной.** Слушает GitHub, решает по ответу классификатора, какой лейбл поставить, ставит его и пишет комментарий |
| `MT lab 7.2 - Issue classifier` | **Sub-workflow.** Только классификация: получает `title` и `body`, возвращает `type` и `confidence`. На GitHub ничего не пишет |

```
Основной:  GitHub Trigger → Is opened? → Classify via sub-workflow → Route by type → лейбл (+ комментарий)
                                                  │          ▲
                                      title, body │          │ type, confidence
                                                  ▼          │
Sub-workflow:                 Execute Workflow Trigger → Classify issue (модель + парсер) → Return type and confidence
```

Между сценариями передаётся только два поля в каждую сторону: `title` и `body` туда, `type` и `confidence` обратно. Классификацию (промпт, модель, парсер) можно менять в sub-workflow, не трогая основной сценарий.

## 3. Основной сценарий по нодам

| Нода | За что отвечает |
|---|---|
| GitHub Trigger (issues) | Принимает события `issues` репозитория |
| Is opened? | Пропускает только `action = opened`, остальное (закрыли, поставили лейбл) уходит в `Ignore: not opened` |
| Classify via sub-workflow | Нода Execute Workflow: вызывает sub-workflow, передаёт `title` и `body`, получает `type` и `confidence`. Если вызов упал, второй выход ведёт в `needs-triage` |
| Route by type | Switch: `bug`, `task`, `feature` при `confidence >= 0.8` идут в свою ветку, всё остальное в запасной выход |
| Label: bug / task / feature-request | HTTP-запрос `POST /issues/{n}/labels` (лейбл добавляется, не заменяя другие) |
| Comment: bug / task / feature | Комментарий-шаблон для автора Issue |
| Label: needs-triage | Лейбл для неуверенных случаев, комментария нет |

## 4. Sub-workflow по нодам

| Нода | За что отвечает |
|---|---|
| Execute Workflow Trigger | Принимает `title` и `body` |
| Classify issue | Basic LLM Chain: промпт описывает типы `bug` / `task` / `feature` / `unknown` и просит оценить уверенность. Текст Issue считается данными, а не инструкциями |
| Chat Model | Модель `anthropic/claude-sonnet-4.5` через шлюз курса |
| Issue type schema | Structured Output Parser: схема ответа (`type` из четырёх значений, `confidence` число 0–1). Auto-Fix включён: при сломанном формате делается одна дополнительная попытка |
| Return type and confidence | Отдаёт наружу ровно два поля |
| Fallback: unknown | Если формат сломан и после Auto-Fix, возвращает `unknown` и `confidence 0`, и Issue уходит в `needs-triage` |

## 5. Что происходит с Issue

| Issue | Ответ классификатора | Результат |
|---|---|---|
| Явный баг с шагами воспроизведения | `bug`, уверенность выше 0.8 | лейбл `bug` + комментарий с просьбой уточнить шаги |
| Вопрос о существующих возможностях | `task`, выше 0.8 | лейбл `task` + комментарий про документацию |
| Просьба новой функции | `feature`, выше 0.8 | лейбл `feature-request` + комментарий |
| Расплывчатое обращение («Иногда не работает») | низкая уверенность или `unknown` | лейбл `needs-triage`, **комментария нет** |

Сбои и неуверенность не теряют Issue: он либо получает свой лейбл, либо `needs-triage`.

## 6. Что сделано по заданию (часть 1)

1. **Классификация и лейблы.** Issue открывается, AI определяет `bug`, `task` или `feature`, Switch ставит нужный лейбл.
2. **Эскалация.** `confidence < 0.8` или неопределённый тип: лейбл `needs-triage`, комментарий не публикуется.
3. **Sub-workflow.** Классификатор вынесен в отдельный сценарий и вызывается нодой Execute Workflow, поведение для всех типов то же.
