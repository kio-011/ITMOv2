# План и состояние: от баг-репорта до исправления в основной ветке (сверхзадача, 10 баллов)

Условие (из README): по баг-репорту автоматически сформировать изменение в коде и запушить его в отдельную ветку, затем провести ревью этого кода и, если серьёзных замечаний нет, смержить в основную ветку. Ядро автоматизации: n8n.

Статус на 2026-11-22: **реализовано и проверено на живом репозитории.** Описание работы для сдачи лежит в [SUPER_TASK_REPORT.md](SUPER_TASK_REPORT.md). Этот файл хранит исходный план и то, чем реализация от него отличается. Основная ветка репозитория `kio-011/subtracker` называется `main` (в условии `master`).

## 1. Схема

Актуальная схема (с классификатором внутри и агентами) лежит в [SUPER_TASK_REPORT.md](SUPER_TASK_REPORT.md). Исходный замысел был таким: Issue с лейблом `bug` → защита от повторов → предпроверка текста → Fixer пишет правки → Guard проверяет границы → ветка и PR → тесты и независимое ревью → merge, повтор или человеку; подозрение на injection на любом шаге ведёт в отдельный статус без повторов.

## 3. Чем реализация отличается от первоначального плана

| Было в плане | Как сделано | Почему |
|---|---|---|
| Запуск по событию `labeled` с лейблом `bug` | Запуск по событию `opened`, внутри вызывается sub-workflow классификатора, дальше только `bug` с уверенностью ≥ 0.8 | Пользователь хотел один публикуемый workflow и видимую связь с классификатором. Событие о лейбле игнорируется, цикла нет |
| Fixer и Reviewer как sub-workflow на цепочке с парсером | Sub-workflow, но оба стали агентами с инструментом `repo_files` (приём из 7.1) и разбором JSON в коде | Первая версия Fixer видела только 3 файла, Reviewer только diff и ложно отклонял верные правки |
| Fixer возвращает файлы целиком | Правки `find/replace` | Меньше токенов, применимость проверяет Guard |
| Reviewer пишет текст | Ответ JSON, вердикт считает код | Нужен машинный формат для ворот |
| Ревью и тесты параллельно | Ревью, затем опрос тестов (CI стартует при пуше и идёт, пока работает ревью) | Проще собрать и проверить |
| Имя ветки `fix/issue-N` | `fix/issue-N-aK-<номер запуска>` | Не конфликтовать с ветками прошлых попыток |
| Ревью с одобрением в GitHub | Ревью комментарием (`COMMENT`) | GitHub не даёт одобрить собственный PR |
| `repo` не вынесен | Репозиторий прописан в URL нод | Один целевой репозиторий |

## 4. Политика повторов и injection

| Ситуация | Что делаем |
|---|---|
| Сбой формата, лимиты нарушены, тесты красные, настоящие замечания ревьюера | Закрыть неудачный PR, одна повторная попытка с причиной, затем `needs-human` |
| Подозрение на prompt injection | `suspected-injection`, без повторов и без merge |

Источники обнаружения injection: предпроверка текста Issue (AI), Guard (тревожные признаки в правке), поле `injection` у ревьюера.

## 6. Что проверено живыми запусками

- Баг про недельную подписку: dry-run (PR создан, ревью и тесты пройдены, merge пропущен), позже PR влит вручную.
- Баг про день месяца: сценарий в боевом режиме сам нашёл причину, PR влит, Issue закрыт, тесты на `main` зелёные.
- Эскалация: два отказа из-за ложного замечания ревьюера (без контекста файла), `needs-human`, один комментарий. Это привело к доработке Reviewer и Fixer.
- Prompt injection: Issue с инструкцией для ИИ остановлен предпроверкой, `suspected-injection`, ни ветки, ни PR.

Не проверено на живых Issue: срабатывание Guard и поля `injection` у ревьюера, повтор с успехом после отказа, правка файла вне набора Locate.

## 7. Известные ограничения и риски

- Fixer читает весь репозиторий, но править может только файлы из набора Locate (до 5); динамическая подгрузка недостающих файлов в Guard не сделана.
- Правка структуры workflow через API снимает его публикацию: после правок через MCP нужно заново нажимать Publish (порядок: Fixer, Reviewer, главный).
- Тесты в `main` не запускаются автоматически (триггеры Actions: PR, `fix/**`, `ci/**`).
- Если сценарий упадёт посреди работы, в `bugfix_runs` останется `running`.
- Предпроверка и поиск файлов выставлены пользователем на Opus 4.5 и 4.7; по расходу достаточно Sonnet 4.5.
